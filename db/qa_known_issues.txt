# =====================================================================
# Known open findings — suites allowed to exit non-zero
# =====================================================================
# Format:  suite | proposal | findings | one-line reason
# Lines starting with # are comments. Blank lines ignored.
#
# A suite listed here is reported KNOWN and does not fail the run. The
# point is to keep the runner usable as a regression gate: a permanently
# red runner tells you nothing, so nobody looks at it.
#
# THE LIST IS SELF-CLEANING, IN BOTH DIRECTIONS.
#   * a listed suite that starts PASSING          -> run FAILS, stale
#   * FEWER findings than the count says          -> run FAILS, narrowed
#   * MORE findings than the count says           -> run FAILS, widened
#
# The count is what makes the middle case visible. Keyed only on
# red-vs-green, a suite holding three findings that drops to one still
# exits non-zero, stays KNOWN, and keeps a reason line describing a
# finding that is already closed -- the file goes on excusing something
# that no longer happens, and nobody notices because the colour did not
# change. That is precisely how a known-issues list rots into a
# permanent excuse.
#
# The last case is the enforcement half of the rule below: without a
# count, a new failure in an already-listed suite is silently absorbed
# by the existing entry.
#
# Nothing may be added to this file to silence a NEW failure. A new
# failure is a regression; it gets fixed or it gets a proposal first.
#
# Put `-` in the findings field for a suite whose summary the runner
# cannot count. That falls back to plain red-vs-green -- honest about
# being weaker, rather than a 0 that would read as "all fixed".
# =====================================================================
